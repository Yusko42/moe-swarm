# Задача #19178: профиль GGUF и оценка памяти

Модуль `model_profile` рассчитывает, сколько памяти потребуется каждому
компьютеру при заданном распределении модели. Вход — GGUF-файл и раскладка
по узлам. Результат — размеры весов, KV и итоговая таблица памяти.

Узел — один компьютер. Раскладка задаёт, какие слои и общие тензоры ему
назначены. Автоматический подбор раскладки в этот модуль не входит.

Команды сборки и запуска, включая `placement.txt`, приведены в
[инструкции запуска](../build.md#запуск-профилировщика-gguf).

## 1. Чтение заголовка GGUF

`read_gguf_header(file)` открывает GGUF в бинарном режиме и возвращает
структуру `GgufHeader`. Поддерживаются v2 little-endian и v3 little/big-endian.

Функция читает:

- сигнатуру `GGUF` и версию формата;
- количество записей метаданных и тензоров;
- метаданные, включая архитектуру и параметры attention;
- описания тензоров: имя, тип хранения, форму и относительное смещение.

Тензор — массив чисел, в котором хранятся веса части модели. Форма определяет
размеры массива. Например, `[256, 3]` означает три строки по 256 чисел
в порядке размерностей GGML.

Сохраняются все ключи и значения, включая строки токенизатора, знаковые
и беззнаковые целые, float32/float64, логические значения и массивы.
Типизированное представление и ограничения описаны в
[контракте ридера](../../src/initiator/model_profile/gguf_reader/README.md).
После описаний тензоров вычисляется начало секции данных
с учётом выравнивания; по умолчанию оно равно 32 байтам.

**Сами веса не читаются и не отображаются в память.** Для проверки смещений
используется размер файла. Проверяются границы, переполнения чисел,
повторяющиеся имена, выравнивание и пересечения тензоров.

У `TensorInfo` поле `offset` отсчитывается от начала секции данных,
а `absolute_offset` — от начала файла. `size_bytes` содержит размер тензора.

## 2. Расчёт размера каждого тензора

Для каждого типа используется пара из таблицы ggml:

```text
{число элементов в блоке, размер блока в байтах}
```

Таблица соответствует закреплённой версии llama.cpp
`cd959bae99ff4bed22bef2604f45241c09bbb8c8`. Позиция записи — числовой ID типа.
Удалённые или неизвестные типы отклоняются.

| Тип | Элементов в блоке | Байтов в блоке |
|---|---:|---:|
| F32 | 1 | 4 |
| F16 | 1 | 2 |
| Q8_0 | 32 | 34 |
| Q4_K | 256 | 144 |

Размер вычисляется по форме:

```text
размер строки = (ne[0] / элементов в блоке) × байтов в блоке
размер тензора = размер строки × ne[1] × ne[2] × ...
```

Первая размерность должна делиться на число элементов в блоке.
Например, Q4_K `[256, 3]` занимает `144 × 3 = 432` байта.
Форма Q4_K `[128, 2]` отклоняется: одна строка не вмещает целый блок.

## 3. Группировка весов

`build_profile(header)` формирует `ModelProfile`:

- `blk.N.*` относится к слою `N`; размеры всех его тензоров суммируются;
- остальные тензоры сохраняются отдельно по именам в `nonblock_tensors`.

Например, `blk.0.attn_q.weight` и `blk.0.ffn_down.weight` входят в веса слоя 0.
`token_embd.weight`, `output.weight` и `output_norm.weight` — внеблочные тензоры.
Их можно назначить разным узлам.

Количество слоёв берётся из `<arch>.block_count`. Некорректные индексы
и отсутствие тензоров какого-либо слоя считаются ошибкой.

## 4. Расчёт KV

KV-кэш создаёт движок во время обработки текста. Это промежуточные данные
для уже обработанных токенов; в GGUF их нет. При работе на CPU кэш занимает
оперативную память. Профилировщик рассчитывает его размер, но не создаёт кэш.

По умолчанию контекст равен 8192 токенам, тип KV — F16, то есть 2 байта
на число. Расчёт для каждого слоя:

```text
KV = head_count_kv × (key_length + value_length) × 2 × 8192
```

Параметры берутся из метаданных `<arch>.attention.*`. Если `head_count_kv`
отсутствует, используется `head_count`. Если отсутствуют `key_length`
или `value_length`, используется `embedding_length / head_count`
с проверкой делимости. Поддерживаются скаляры и массивы параметров по слоям.

Для конфигурации Qwen3-30B-A3B из задачи: 4 KV-головы, явные длины K и V
по 128, 48 слоёв. При 8192 токенах это 16 MiB на слой и 768 MiB всего.
Для 24 слоёв одного узла — 384 MiB KV. Контекст можно изменить через
`--context N` или аргумент `build_profile(header, context_tokens)`.

## 5. Раскладка и таблица памяти

`estimate_ram(model, nodes)` получает список `NodePlacement`. Каждый элемент
задаёт имя узла, диапазон слоёв `[first, end)`, внеблочные тензоры,
`engine_buffer_bytes`, `overhead_bytes` и `limit_bytes`.

Диапазон `[0, 24)` включает слои 0–23. Каждый слой должен быть назначен ровно
одному узлу, каждый внеблочный тензор — хотя бы одному. Явное размещение
одного внеблочного тензора на нескольких узлах учитывает отдельную копию
на каждом из них. Повторение внутри одного узла отклоняется.

Функция возвращает список `NodeMemory`; CLI выводит его в виде таблицы:

| Поле вывода | Что означает |
|---|---|
| `name` | Имя узла |
| `weights` | Сумма весов назначенных слоёв |
| `nonblock` | Сумма назначенных внеблочных тензоров |
| `kv` | KV-кэш назначенных слоёв |
| `engine` | Буферы движка, заданные параметром |
| `overhead` | Обвязка, заданная параметром |
| `total` | Сумма `weights + nonblock + kv + engine + overhead` |
| `limit` | Заданный лимит памяти |
| `fits` | `yes`, если `total <= limit`, иначе `no` |

Все расчёты выполняются в байтах. CLI по умолчанию показывает таблицу узлов
в MiB, с `--bytes` — в точных байтах. Буферы движка, обвязка и лимит
задаются пользователем, а не извлекаются из GGUF.

Из C++ последовательность вызовов выглядит так:

```cpp
auto header = swarm::read_gguf_header("model.gguf");
auto model = swarm::build_profile(header);  // 8192 токена, F16 KV
auto table = swarm::estimate_ram(model, nodes);  // nodes: vector<NodePlacement>
```

## Границы реализации

RAM-профиль поддерживает стандартный attention для архитектур `llama`,
`mistral`, `qwen2`, `qwen2moe`, `qwen3`, `qwen3moe`. Для MLA и гибридных
архитектур нужны другие формулы. Профиль модели из нескольких GGUF-шардов
отклоняется; отдельный заголовок можно посмотреть через `--header-only`.

Результат — расчёт памяти для заданной раскладки. Он не запускает модель,
не распределяет слои автоматически и не измеряет фактическое потребление RAM.
