# М-04c. Пользовательский systemd и профиль CI

При входе по SSH пользовательский scope запускался в обоих режимах linger.

- `Linger=no`: через 45 с после выхода повторный вход показал, что идентификатор менеджера изменился, а scope исчез.
- `Linger=yes`: менеджер сохранил прежний идентификатор, и scope остался активным.

Когда шина пользователя была недоступна, проба вернула `cgroup_unavailable` (код 78). Сообщение предлагало проверить состояние менеджера командой `systemctl --user status`, вход через PAM, переменную `XDG_RUNTIME_DIR`, шину и делегирование контроллера памяти.

В контейнере отсутствовал `systemd-run`, поэтому попытка создать пользовательский scope завершилась с кодом 78 и подсказкой применить внешний лимит. С лимитом Docker проба прочитала `memory.max=134217728` и `memory.swap.max=0` и завершилась с кодом 0.

При `ManagedOOMMemoryPressure=auto` нагрузка завершилась за 35,1 с с кодом 0. При `ManagedOOMMemoryPressure=kill` служба `systemd-oomd` завершила процесс через 13,1 с (код 137), хотя для дочернего scope действовала политика `OOMPolicy=continue`.

В прогоне `m04c-no-exL4VDge` сборщик вернул `collection_rc=1`: в его выборке журнала отсутствовала запись oomd. На гостевой Ubuntu `systemd-oomd` убила процесс в `m04ckill246219572.scope`, когда давление в родительском slice достигло 9,24% и превышало порог 5% дольше 5 с. Прогон `m04c-yes-lBRG4jIx` завершился с `collection_rc=0`.

## Как повторить

- Команды должны запускаться из `moe-swarm`.
- Нужен пользователь без запущенных сеансов и с доступом к Docker и журналу oomd.

```bash
bench=qa@bench-host
export M04C_IMAGE=ubuntu@sha256:d66b366dac61b575bee2aef07e9c26e8070096fbe84a3d4d3eb0da069b5d76db

# На стенде: sudo loginctl disable-linger qa
./experiments/m04-c/collect.sh "$bench" no

# На стенде: sudo loginctl enable-linger qa
./experiments/m04-c/collect.sh "$bench" yes
```

Сборщик сохраняет `before.log`, `after.log` и `logout.txt` в каталогах `m04c-no-*/` и `m04c-yes-*/` на клиенте.
