# Методика измерений MoE Swarm (проект, v0.1)

**Назначение:** получать сопоставимые измерения на стенде из трёх ПК при одинаковых версии ПО, модели, запросах, режимах кэширования и условиях нагрузки. Данный документ определяет измерения, но **не заменяет** ФТ/НФТ и чек-листы по ФТ.

## 1. Основания и границы

- НФТ #18326: https://ai.nsu.ru/issues/18326 (актуальную редакцию проверять перед прогоном).
- «План тестирования»: https://ai.nsu.ru/documents/934. Из него взяты требования к прогреву, отсутствию посторонних запросов и воспроизводимости проверок.
- Wiki MoE Swarm: в ней определены «скорость генерации» и «пробный запрос». Для официального замера НФТ-1 использовать **именно запрос из Wiki**, а не заменять его корпусом данного каталога.
- Дополнительно для технической реализации: документация `llama-server` (`GET /health`, `/apply-template`, `/tokenize`, `timings`) — https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md.

Числовые цели принимать только из актуальных НФТ: например, НФТ-1 — не менее **16 т/с** по 10 учитываемым запросам. Значение «после первого замера» у НФТ-6–8 **не является заданной числовой целью**. Не объявлять испытание пройденным по выдуманному порогу.

**Разные уровни запуска:** `llama-server` (процесс сервера) и `/start` (команда MoE Swarm) могут иметь разные времена. Результаты не смешивать. Аналогично различать ожидание **в очереди**, ожидание **до первого ответа** и собственно **скорость генерации**.

## 2. Единый словарь событий и метрик

Во всех измерениях времени использовать монотонные часы **на одной стороне измерения**; время в ISO 8601 с часовым поясом служит для сопоставления отчётов, но не для вычитания отметок разных компьютеров. В журналах для каждого события сохранять `run_id`, при необходимости `request_id`, `node_id`, `event`, `timestamp_monotonic_ns` и `timestamp_utc`; текст запросов и ответов в технические журналы **не записывать** (НФТ-9).

| Показатель | Единица | Начало → конец | Источник | Правило / оговорка |
|---|---|---|---|---|
| `server_startup_s` | с | Непосредственно перед созданием процесса `llama-server` → получение завершённого HTTP-ответа `GET /health` со статусом 200 | Обёртка запуска и локальный HTTP-клиент | Замерять с той же машины, фиксировать интервал опроса (например, 0,1 с), PID, код возврата; HTTP 503 означает «ещё загружается». **Не подменяет НФТ-6.** |
| `swarm_startup_s` (НФТ-6) | с | Отправка `/start` → событие «модель готова» | Журнал/инструментирование Инициатора | Должно включать именно те этапы, которые определены актуальным ФТ-1; не приравнивать к `server_startup_s`. |
| `ttft_client_s` | с | Непосредственно перед отправкой HTTP-запроса → получение первого **непустого фрагмента содержимого** ответа в streaming-клиенте | Клиент с монотонными часами | Не считать SSE-соединение, пустые delta, служебные поля, keep-alive или reasoning первым токеном. Потоковый фрагмент может содержать несколько токенов: это **наблюдаемая клиентом аппроксимация**, а не точная серверная отметка токена. |
| `ttft_server_s`, если реализовано | с | Приём запроса сервером → генерация первого выходного токена | Инструментирование сервера | Отдельный показатель; не смешивать с клиентским TTFT. |
| `prompt_tps` | токен/с | Начало фактической обработки входа → завершение prompt evaluation | Счётчики и timings движка (`prompt_n`, `prompt_ms` или эквивалент) | `prompt_tps = N_фактически_обработанных / (prompt_ms/1000)`. При reuse учитывать только **обработанные**, а не все токены контекста. Фиксировать число кэшированных токенов. |
| `generation_tps` | токен/с | Начало декодирования выходных токенов → окончание стадии декодирования | Отдельные timings движка (`predicted_per_second` либо n/time) | Не делить на полное время запроса. Использовать согласованное определение из Wiki и поля конкретной версии движка. В некоторых версиях llama.cpp decode-steps = число выходных токенов − 1; записывать формулу и исходные счётчики. |
| `memory_current_bytes` | байт | Периодическая выборка раз в 1 с на протяжении фазы | Linux cgroup v2: `memory.current` | Для каждого узла отдельно; указать путь к cgroup и состав входящих процессов; не путать с объёмом установленной RAM. |
| `memory_peak_bytes` | байт | От старта отдельного прогона до завершения | Linux cgroup v2: `memory.peak` | Использовать **отдельную cgroup на прогон** или проверенный сброс пика. Пик по отсчётам `memory.current` — другой, менее надёжный показатель. |
| `queue_wait_s` | с | Принятие запроса в очередь → извлечение из очереди/начало обслуживания | Журнал Инициатора с `request_id` | **Не включает** последующую обработку prompt и генерацию. Не вычислять как TTFT. Если отметки нет — `не измерено`. |
| `request_to_answer_s` (НФТ-8) | с | Приём запроса системой → событие «начало ответа», трактовка которого согласована с командой | Журнал Инициатора с `request_id` | НФТ-8 описывает именно этот интервал; пока «начало ответа» не определено точнее, хранить исходные отметки и не приравнивать автоматически к `queue_wait_s` или клиентскому TTFT. |
| `request_total_s` (доп.) | с | Отправка запроса клиентом → окончание ответа | Стриминговый клиент | Включает очередь, prompt, генерацию, транспорт и накладные расходы; **не является** скоростью генерации. |

Пример основных событий для реализации в коде (имена событий **предлагаемые**, не утверждённый API): `swarm_start_requested`, `model_ready`, `request_received`, `request_queued`, `request_dequeued`, `prompt_eval_started`, `prompt_eval_finished`, `first_token_generated`, `response_started`, `generation_finished`, `rebuild_started`, `rebuild_ready`. Нужна корреляция по идентификатору одной операции; значения времени измеряются с одного процесса/монотонной шкалы либо передаются рассчитанные локально длительности.

**Происхождение источников:** величины из клиентских измерений, логов Инициатора, встроенных timing-полей сервера и OS/cgroup — **разные типы источников**, в таблице результатов указывать `source`, не агрегировать без согласования.

## 3. Эталонная конфигурация и запись окружения

Перед измерением заполнить `report-template.md`: `stand_id`, роли узлов, CPU, тип/частота/канальность RAM, SSD, ОС, сетевой адаптер и линк ≥ 1 Гбит/с, конфигурация `--memory`, версии драйверов/бинарников и commit, состояние процессов. Базовый НФТ-1: 3 ПК × 8 ГБ установленной RAM, каждому рою выделено 6 ГБ; CPU-only; Qwen3-30B-A3B Q3_K_M; KV FP16 по слоям; context limit 8192; один активный ответ; без подгрузки весов с SSD при распределённой генерации.

Зафиксировать: точный файл GGUF, путь к нему (в доступном QA-манифесте), размер и SHA-256; версию/tokenizer/chat template, настройки памяти, threads, batch, наличие и режим KV/prompt cache, сведения о сети (RTT и проверенную скорость линка), версии Linux kernel/cgroup или методику Windows, наличие swap. Если сравниваются режимы одного ПК и роя, аппаратные отличия указывать явно.

Обязательно проверять отсутствие интенсивной посторонней нагрузки; не считать стенд изолированным только на основании отсутствия активного пользователя. Фиксировать загрузку CPU, RAM, сети до прогона и во время прогона. Отключить параллельные пользовательские запросы.

## 4. Корпус запросов и проверка длины

Файлы `corpus/` — **специально подготовленные синтетические тексты**, не пользовательские данные: короткий контрольный запрос, ~1k, ~4k и «около 8k» токенов, многоходовый диалог. Это нагрузочные сценарии для анализа TTFT/prompt и поведения при длительном контексте; для официального НФТ-1 использовать пробный запрос Wiki.

1. До замеров запустить `corpus/generate.py` и сверить текст и хеши с `corpus/manifest.json`. Перед первым испытанием на конкретном GGUF откалибровать токены через **реальный tokenizer с финальным chat template**, а не по словам/символам. В каталоге лежат начальные **некалиброванные** версии; подписи 1k/4k/8k — целевые профили, не доказанные количества токенов.
2. Фиксировать `prompt_tokens_total` (после шаблона), `cached_tokens`, `new_prompt_tokens`, `max_new_tokens`, число служебных токенов.
3. При лимите контекста 8192 и длине ответа 256 должно выполняться `prompt_tokens_total + 256 <= 8192` (с запасом на особенности сервера/шаблона). Профиль «8k» поэтому означает **контекст около лимита**, для начала рекомендуемый ориентир — до **7800 входных токенов включая шаблон**, а не 8192 + 256. Если порог не выдержан — текст уменьшить и пересчитать.
4. Многоходовый сценарий содержит фиксированную **синтетическую** историю, чтобы нагрузка была воспроизводима без зависимости от непредсказуемых предыдущих ответов. Отдельно можно тестировать реальный интерактивный диалог, но не смешивать результаты с синтетическим воспроизведением истории.
5. Корпус, манифест и правило исключения из логов пользовательского содержимого не противоречат друг другу: тексты специально созданы для QA, но журнал системы всё равно должен хранить лишь технические метаданные.

Профили 1k/4k/8k — **дополнительная матрица**, не заменяющая условия НФТ-1 (пробный запрос Wiki). Для сравнения между днями сохранять тот же файл корпуса и его SHA-256.

## 5. Настройки генерации и кэширования

**Базовое предложение для утверждения** (не самовольно новый НФТ): `temperature = 0` (или согласованный фиксированный `seed` и все параметры сэмплинга), `max_new_tokens = 256`, `thinking = off`, 1 прогревочный запуск + **10 учитываемых успешных прогонов** на измеряемый сценарий. Для отчёта считать арифметическое **среднее и медиану**, по возможности минимум/максимум. Если модель завершает ответ по EOS раньше 256 токенов, фиксировать `stop_reason` и фактическое число токенов; нельзя записывать «256» по одному лишь параметру максимума. Режим принудительной длины (`ignore_eos`) можно использовать только если движок его поддерживает и команда одобрит — фиксировать в конфигурации.

Для Qwen3 важен способ отключения размышлений: корректный `enable_thinking=false` в используемом chat template / API, либо согласованная альтернатива, подтверждённая тестом. Одного поля в отчёте недостаточно. В Qwen3 soft-switch `/no_think` не во всех конфигурациях эквивалентен hard-switch.

**Два отдельных профиля кэша:**
- `COLD_PROMPT`: повторное использование prompt/KV cache выключено или гарантированно сброшено перед *каждым* учитываемым прогоном. Измеряет полную обработку входа.
- `MULTITURN_CACHE`: кэш намеренно включён, история нарастает по фиксированному сценарию. Зафиксировать cache hit/reused tokens. Запрещено смешивать с `COLD_PROMPT` в общей статистике.

Если сервер не умеет гарантированно отключать/сбрасывать кэш, пометить профиль как не воспроизводимый и согласовать эквивалентный способ (отдельный слот/новый процесс). В новых версиях llama.cpp prompt cache может быть включён по умолчанию: проверять реальные настройки и поле кэшированных токенов, а не надеяться на порядок запусков.

Перед каждым сценарием одинаково определять: reset/restart policy, one-server/one-model режим, фиксированные параметры threads/threads-batch, batch size, число слотов, prompt template, seed, temperature/top-k/top-p, параметры sampling, stop/eos, максимальный контекст и лимит ответа.

## 6. Порядок прогонов

1. По `checklists.md` пройти этап **до прогона**. Назначить `run_group_id`, проверить манифест стенда, модель, сеть, нагрузку и источники времени/памяти.
2. Сохранить значения параметров в отчёте и подготовить мониторинг RAM **до** запуска измеряемого процесса/модели. Для измерения холодного старта явно остановить старый `llama-server` и убедиться, что `/health` ещё не 200.
3. Выполнить 1 warm-up с тем же профилем, результат **не учитывать**. Для `COLD_PROMPT` после warm-up снова обеспечить холодное состояние перед первым учитываемым прогоном. Состояние кэша и политику рестарта записать.
4. Выполнить 10 валидных учитываемых прогонов на сценарий. Сохранять **сырой ряд из 10 значений**, timestamp начала, статус, потери/ошибки, счетчики токенов и источник метрики. Ошибочные/прерванные прогоны не удалять: помечать `INVALID`, причину и дополнительный повтор отдельной строкой. Нельзя выбирать только удачные быстрые прогоны.
5. После серии вычислить среднее (сумма 10 значений / 10) и медиану (полусумма 5-го и 6-го отсортированных значений), число ошибок отдельно. Указывать объём выборки.
6. Зафиксировать изменения конфигурации при переходе между профилями. Не смешивать результаты с разной моделью, кэшем, числом узлов, настройками sampling или длиной входа.
7. Пройти этап **после прогона** и приложить отчёт с ссылками на файлы измерений и логи.

## 7. Уточнение реализации измерений

### Старт сервера

На тестовом ПК создать процесс `llama-server`; непосредственно перед его запуском записать `monotonic t0`, затем опрашивать `GET http://127.0.0.1:<PORT>/health` с интервалом 0,1 с и ограничением ожидания. Как только завершён запрос с HTTP 200, записать `monotonic t1`. `server_startup_s = (t1-t0)`. HTTP 503 — загрузка; таймаут, раннее завершение или другой код — отдельный исход, не числовая успешная длительность. Записывать точные бинарник, аргументы и интервал опроса.

### Клиентский TTFT

Использовать streaming API, у клиента часы `monotonic_ns`; взять `t0` **перед сетевой отправкой**. В SSE-потоке игнорировать пустые строки, keep-alive, role-only events, usage, reasoning и пустые дельты; взять `t1` на первом содержательном фрагменте `content`. Для HTTP/chunked это оценка времени появления контента на клиенте, на которую влияет сеть и буферизация. Для точного серверного «первого токена» нужно отдельное событие сервера.

### Input throughput и decode throughput

Предпочесть внутренние timing-поля **именно используемой версии** `llama-server`; сохранить их оригинальные названия и значения. Для новой реализации llama.cpp число output *decode steps* может не совпадать с числом output tokens (первый токен вычислен в конце prompt stage), поэтому источник и знаменатель `generation_tps` закрепить в отчёте. Если timings недоступны — показатель `не измерен`, а не `output_tokens / request_total_s`.

### RAM

Linux + cgroup v2: раз в 1 с читать `memory.current`, после прогона `memory.peak` и при наличии `memory.swap.current`; фиксировать cgroup-путь, процессы, ограничения `memory.max` и время начала считывания. Не считать `memory.peak` «пиком с первой секунды замера», если cgroup существовала до прогона. На Windows зафиксировать выбранные PerfMon/ETW/системные счётчики и их смысл; напрямую не сравнивать их с cgroup-метриками как будто это идентичные показатели. Для сравнения с отданными 6 ГБ согласовать единицы (ГБ/ГиБ) и состав учитываемой памяти.

### Очередь

Нужны два события **в одном журнале Инициатора**: `request_received` и `request_dequeued` / `request_processing_started`; их разность — `queue_wait_s`. Для НФТ-8 дополнительно записывать отдельное событие `response_started` согласно согласованной трактовке. Если соответствующих событий нет, нужен тикет разработчикам на инструментирование; клиентский TTFT не заменяет серверные логи очереди.

## 8. Статусы, отклонения, QA-процесс

- `PASS / FAIL` ставить только при наличии **принятого** ожидаемого результата из актуальных требований. Иначе `MEASURED / TBD` либо `BLOCKED`.
- При отсутствующей реализации источника метрики писать `NOT INSTRUMENTED`, при отсутствующей конфигурации — `BLOCKED`, при неверных условиях — `INVALID CONFIGURATION`.
- Перед созданием нового тест-кейса проверять соответствующий **общий чек-лист**, чтобы не дублировать существующую проверку. Эти файлы описывают только общую методику измерений, не подменяют чек-листы ФТ.
- Новые найденные ошибки оформлять по общему QA-шаблону и связывать с требованием, конфигурацией стенда и прогоном.

## 9. Вопросы к разработчикам/аналитикам перед утверждением v1.0

1. Реализован ли потоковый API, который даёт **первый непустой токен**, а не только фрагменты текста? Согласовать `ttft_client` как основной или добавить серверное событие.
2. Какие поля с корректными счётчиками и timings доступны в вашей закреплённой версии `llama-server`? Какой точно числитель у `generation_tps` по Wiki?
3. Совпадает ли запуск `llama-server` с командой `/start`? Для НФТ-6 **обязательно** нужен отдельный отмер от `/start`, если это разные операции.
4. Как определить «начало ответа» в НФТ-8: начало генерации, первый токен или первое появление текста в чате?
5. Можно ли строго отключить thinking и prompt cache; как обеспечивается 256 выходных токенов без преждевременного EOS?
6. Есть ли поддержка `memory.current/peak` на выбранных ОС и как учитываются дочерние процессы/RPC-соседи?
7. Какие параметры (включая KV-кэш) считаются обязательными для базового НФТ-1, и нужна ли отдельная методика с mmap для НФТ-2.1?

После ответов на вопросы оформить решение в issue/PR и зафиксировать версию методики. Менять методику задним числом **после** получения результатов нельзя без отмеченного пересчёта и сохранения старой версии.
