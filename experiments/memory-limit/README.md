### Ограничение памяти на группу процессов

Задача: вся программа узла должна занимать не больше 8 ГБ: агент и rpc-server у соседа, инициатор и llama-server у инициатора. Нужен готовый механизм Linux без прав root и способ убрать процессы, если владелец упал.

#### 1. Как ограничить общую память
Есть cgroup v2. Он позволяет объединить несколько процессов в группу и установить для них общий предел памяти. Механизм доступен обычному пользователю через `systemd-run`. Для запуска задаются две настройки:
- `MemoryMax=8G` - общий предел оперативной памяти;
- `MemorySwapMax=0` - запрет переносить данные этой группы в swap, то есть во временную область на диске.
Запускаемая программа сразу оказывается внутри ограниченной группы. Программы, которые она запускает сама, наследуют ту же группу. Поэтому агент и rpc-server используют **один общий лимит**.

#### 2. Как проверялось превышение лимита
Ставил лимит 1 ГБ. Тестовая программа запускала двух потомков. Каждый пытался занять 640 МБ, то есть вместе больше предела. Измеренный пик памяти группы составил ровно 1 ГБ. После этого произошло принудительное завершение процессов из-за нехватки памяти (OOM).

Проверены три варианта поведения:

| Настройка            | Что произошло в опыте                                                                  |
| -------------------- | -------------------------------------------------------------------------------------- |
| По умолчанию         | Ядро Linux завершило одного потомка, затем systemd остановил остальные процессы группы |
| `OOMPolicy=continue` | Один потомок погиб, родитель и второй потомок продолжили работу                        |
| `OOMPolicy=kill`     | Завершились все три процесса                                                           |

То есть можно поставить continue, чтобы агент мог сообщить об ошибке, но не факт, что ядро выберет именно движок.

#### 3. Проверка swap и рабочего лимита
По умолчанию системе доступно 4 ГБ swap. При `MemorySwapMax=0` тестовая группа не использовала swap и при нехватке памяти получила OOM. Без запрета та же нагрузка заняла 273 МБ swap, и оба потомка смогли продолжить работу.

Рабочий лимит 8 ГБ также проверен - все процессы увидели правильное ограничение.

#### 4. Как программа узнаёт свой расход памяти
Linux предоставляет показатели группы в виде файлов:

| Файл             | Что узнает программа                                         |
| ---------------- | ------------------------------------------------------------ |
| `memory.max`     | Сколько памяти разрешено использовать                        |
| `memory.current` | Сколько используется сейчас                                  |
| `memory.peak`    | Какой расход был максимальным                                |
| `memory.events`  | Были ли достижения лимита и завершения из-за нехватки памяти |

В опыте с `continue` счётчик `oom_kill` увеличился на один: ядро завершило один процесс из-за нехватки памяти.

#### 5. Что происходит после остановки агента
Одна только ограниченная группа не завершает потомков вслед за родителем. Без дополнительной настройки оба потомка оставались работать после обычного выхода, Ctrl+C и принудительного завершения родителя командой `kill -9`.

Для автоматической остановки потомок устанавливает `PR_SET_PDEATHSIG(SIGKILL)` (если мой родитель завершится, заверши и меня). В таком случае потомки завершили работу во всех экспериментах.

При штатной остановке агент должен сначала попросить rpc-server завершиться, дождаться его и только при необходимости завершить принудительно. PDEATHSIG нужен как страховка на случай аварии агента.

#### 6. Рекомендация для swarm
Рекомендуется встроить проверку лимита в запуск swarm. Если нужной группы ещё нет, программа перезапускает себя через `systemd-run` и продолжает работу уже под ограничением. Пользователь запускает swarm обычной командой, без отдельной обертки.

Если установить лимит не удалось, программа должна сообщить об ошибке и завершиться до запуска rpc-server и загрузки модели.

### По коду

Основной код полезный для swarm в `limits.hpp`:
1. `enter_limited_scope()` проверяет ограничение памяти. Если процесс ещё вне нужной группы, он заменяет себя через `exec` на `systemd-run --user --scope`, который запускает тот же бинарник уже с `MemoryMax=8G` и `MemorySwapMax=0`. PID сохраняется.
2. `read_memory()` читает состояние группы: лимит, текущий расход, пик, swap, события OOM, отдельно анонимную память и файловый кэш.
3. `spawn_bound()` запускает rpc-server. Потомок наследует cgroup и перед `exec` устанавливает `PR_SET_PDEATHSIG(SIGKILL)`: после смерти создавшего его потока ядро отправит ему SIGKILL. Проверка `getppid()` закрывает гонку, когда агент умер ещё до настройки сигнала.
4. `stop_bound()` обеспечивает штатную остановку: SIGTERM группе процессов rpc-server, ожидание до трёх секунд, затем SIGKILL и `waitpid`.

`swarm_demo.cpp` это пример как использовать `limits.hpp` в нашем проекте. Он читает параметры запуска, ограничивает память, запускает моковый rpc-server, ждет команд пользователя и затем выходит.

`workload.cpp` - это программа, которая создает нагрузку на память. `workload parent` создает родителя, который вызывает два раза `workload child`. Потомок постепенно выделяют память, пока не займет 640 МБ. Лимит группы 1024 МБ. Проверяются различные параметры и способы завершения.

`run_scenarios` - это скрипт, который запускает все эксперименты. `Terminal` запускает программу через виртуальный терминал (можно проверять нажатие клавиш). `Sentinel` проверяет, пострадало ли что-то вне группы. `run_case()` запускает сценарий с параметрами.

`check-env.sh` проверяет, поддерживает ли система ограничение памяти без root.

`build.sh` собирает две C++ программы.

`run-in-scope.sh` запускает переданную программу внутри группы с лимитом памяти.
